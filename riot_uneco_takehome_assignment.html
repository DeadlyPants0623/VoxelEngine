Assignment 01
The Diagnostic Plugin
Plugin architecture · Subsystems · Runtime tooling
Recommended starting point
Scenario
A game team is reporting intermittent slowdowns and crashes during development but can't pinpoint the source. They need a lightweight diagnostic plugin they can drop into any UE5 project without modifying game code. You've been asked to build it.
Deliverables
  • Create a C++ plugin named RiotDiagnostics with correct .uplugin and Build.cs structure
  • Implement a UGameInstanceSubsystem that on Initialize() logs: total actor count, platform memory stats via FPlatformMemory::GetStats(), and loaded asset count via FAssetRegistryModule
  • Register a console command riot.diag.dump that re-triggers the full diagnostic report at any point during PIE
  • Define and use a custom log category LogRiotDiag consistently across all plugin files
  • Write the diagnostic output to a timestamped .txt file under Saved/Diagnostics/
What we're evaluating
Plugin structure
Correct module layout, no shortcuts
Subsystem lifecycle
Proper Initialize / Deinitialize usage
Engine API fluency
Use of FAssetRegistry, FPlatformMemory
Code clarity
Readable by a game team engineer
Assignment 02
The Asset Validator
Commandlet · Pipeline tooling · Automation tests · Editor extensions
Intermediate
Scenario
Riot's art pipeline requires all StaticMesh assets to follow strict naming and LOD conventions. Meshes that don't comply cause downstream build failures. You've been asked to build a tool that validates these rules automatically — both from the command line and from within the editor.
Deliverables
  • Create a C++ plugin named RiotAssetValidator with proper editor-only module separation in Build.cs
  • Implement a UCommandlet that accepts a content directory path as an argument and flags any StaticMesh that: does not begin with SM_, is missing LOD1, or exceeds a triangle count threshold configurable via DefaultRiotValidator.ini
  • Output a validation report to Saved/ValidationReports/report.csv with columns: asset path, violation type, detail
  • Add an editor toolbar button or Editor Utility that runs the same validation scoped to assets used in the currently open level only
  • Write at least one FAutomationTestBase test that validates your commandlet logic against mock asset data
What we're evaluating
Build.cs discipline
Runtime vs editor module split
Commandlet pattern
Core of Riot's pipeline tooling
Testable code
Logic separated from UE5 glue
Editor integration
Clean toolbar or utility hook
Assignment 03
The Ecosystem Bridge
Interop · Memory safety · Slate · System design
Advanced
Scenario
A game team needs a lightweight event broadcasting system that works seamlessly across C++, Blueprint, and editor tools — without any of those layers needing to know about each other. You've been asked to design and build this system as a standalone plugin.
Deliverables
  • Create a C++ plugin named RiotEventBus
  • Implement a UGameInstanceSubsystem that allows any C++ class to register a listener against a named FGameplayTag event
  • Expose a UFUNCTION(BlueprintCallable) method BroadcastEvent(FGameplayTag Tag, FString Payload) callable from Blueprint
  • Use TWeakObjectPtr for listener storage so that listeners owned by GC'd objects are automatically cleaned up without crashing
  • Provide a minimal working demo: one Blueprint actor broadcasts Event.Player.Died, one C++ actor listens and logs the payload
  • Add a Slate-based editor tab showing a live event feed during PIE — displaying tag name, payload, and timestamp for each broadcast
What we're evaluating
C++ ↔ BP interop
Correct UFUNCTION exposure
Memory safety
TWeakObjectPtr listener cleanup
Slate basics
Functional editor panel
System design
Can you explain the why, not just the what
